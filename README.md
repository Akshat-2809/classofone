# Class of One — getclassofone.com

Production site for Class of One: live one-on-one classes for school children. It's a faithful port of the approved homepage design plus the waitlist backend.

Everything lives in one Next.js 16 app in [`web/`](web/). The forms are handled by **Server Actions** in the same app, so there is no separate API service. They write to Postgres (Neon) and send emails through Resend. This is the same setup as doomcure and squarebookai.

## Local setup

Requirements: Node 20.9 or later, and a Postgres database.

```bash
cd web
npm install
cp .env.example .env.local      # then fill in the values
npm run db:migrate              # creates the hand_raises and contact_messages tables
npm run dev                     # http://localhost:3000
```

Postgres for local work, pick one:

- **Docker:** `docker run --name classofone-pg -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=classofone -p 5432:5432 -d postgres:17`. This matches the default `DATABASE_URL` in `.env.example`.
- **Neon:** create a free project and use a dev branch's connection string.

If `RESEND_API_KEY` is empty, the forms still work and the emails are skipped with a log line.

## Environment variables

| Variable | Required | Notes |
|---|---|---|
| `DATABASE_URL` | yes | Postgres connection string. Use Neon's **pooled** URL on Vercel. Without it, the forms show an error asking people to email instead. |
| `IP_HASH_SALT` | yes in production | Random string (`openssl rand -hex 32`). IPs are stored only as salted hashes, for rate limiting. |
| `RESEND_API_KEY` | for email | From resend.com → API Keys. |
| `EMAIL_FROM` | for email | `Class of One <hello@getclassofone.com>`. The domain must be verified in Resend. |
| `NOTIFY_EMAIL` | for email | Inbox that receives each new hand-raise and contact message. |
| `NEXT_PUBLIC_SITE_URL` | no | Defaults to `https://getclassofone.com`. Used for canonical URLs, sitemap and OG tags. |

## How the "Raise my hand" form works

1. The form posts to the `raiseHand` Server Action (`src/app/actions/raise.ts`) with `useActionState`: name, email, audience (from "I'm a…"), one audience-specific detail, and the honeypot `website`.
2. If the honeypot is filled, the action returns a normal-looking success and stores nothing.
3. zod validates the input. The email is trimmed and lowercased. The detail must be one of the listed classes (parent) or subjects (teacher), or a full http(s) link (curriculum maker).
4. Rate limit: 10 per IP per hour, counted in Postgres (indexed on `ip_hash, created_at`). This works across serverless instances.
5. The row goes into `hand_raises`: `id, name, email, audience, detail, created_at, ip_hash, user_agent`. Email and audience are unique together, so one person can be both a parent and a teacher. A duplicate is treated as success, with no error and no second email.
6. Both emails are sent with `after()`, once the response has gone out: the thank-you ("Pratik will reach out personally.") and the notification to `NOTIFY_EMAIL`. An email failure is logged and never fails the signup.
7. UI states: idle → submitting (button disabled + spinner, screen-reader announcement) → success (the hand goes up and earns its gold star) or error (next to each field, keeping what the person typed).

`GET /api/waitlist/count` returns `{ count }`, cached for 60 seconds. It's for the founder and isn't linked anywhere on the site.

## How the contact form works

`/contact` uses the same pattern. `ContactForm` posts to the `sendContactMessage` Server Action, with the same honeypot, zod validation (name, email, a message of 10 to 5,000 characters) and a limit of 5 messages per IP per hour. Messages go into `contact_messages`. The message is forwarded to `NOTIFY_EMAIL` with reply-to set to the sender, and the sender gets a short acknowledgement.

## Deploy to Vercel

1. Push the repo to GitHub, GitLab or Bitbucket, then in Vercel choose **Add New → Project** and import it.
2. Set **Root Directory** to `web`. The framework preset (Next.js) and the build command are detected automatically.
3. **Database:** Project → **Storage** → **Create Database** → **Neon (Postgres)**, and connect it to the project. This adds `DATABASE_URL` to the environments you choose.
4. Add `IP_HASH_SALT`, `RESEND_API_KEY`, `EMAIL_FROM` and `NOTIFY_EMAIL` under Settings → Environment Variables, for Production (and Preview if you want previews to send emails).
5. Run the migration once against the production database, from your machine:
   ```bash
   cd web
   DATABASE_URL="<Neon connection string from Vercel>" npm run db:migrate
   ```
   Repeat this whenever you add a migration.
6. Deploy. Preview deployments serve a `Disallow: /` robots.txt, so they stay out of search results.

## Connect the domain

1. In Vercel: Project → **Settings → Domains** → add `getclassofone.com`, then `www.getclassofone.com`, and choose to **redirect `www` to the apex**.
2. Vercel shows the exact DNS records to create (typically an **A** record for `@` and a **CNAME** for `www`). Add them at your domain registrar, removing any default "Parked" records first.
3. Wait for both domains to show **Valid Configuration**. HTTPS certificates are issued automatically.

To send email: in Resend, **Domains → Add Domain** → `getclassofone.com`, add the DNS records it lists, click **Verify**, and set `EMAIL_FROM` to an address on that domain. Resend only sends. To *receive* mail at hello@getclassofone.com, set up a mailbox provider (Google Workspace, Zoho, etc.) and add its MX records.

## Fidelity notes (vs. the approved design, `Main.dc.html`)

Compared side by side in Chrome at 1440px and 390px:
- **Layout:** every section has the same top and height as in the design at 1440px, except the report card, which is taller for the photo. At 390px the page is also slightly taller, for the nudge change below.
- **Pixel difference:** 0.00% on most sections. The rest comes from animations caught at a different moment and the live clocks.
- **Interactions:** all checked in the browser (notebooks, nav switch, pinned timetable and period buttons, nudges, interest chips, minutes chart, clocks, report card, form states).

Intentional differences:
- **Waitlist is real.** The design's form only flipped to a thank-you. It now validates and stores. After signing up as a parent, switching to Teacher brings the form back rather than claiming "You're on the list as a teacher".
- **Pages added:** Privacy and Terms are real pages, linked from the navbar and the footer. A Contact page was added, and the email is a `mailto:` link. Nav and footer links point to `/#section`, so they work from every page. The "I'm a…" switch shows only on the homepage.
- **Footer redesigned:** the design's "School's out" bell and "Tomorrow's timetable" list became four columns (brand, Explore, Policies, Raise your hand), keeping the chalkboard and wooden ledge. The email box stores nothing itself: it carries the email to the "Raise my hand" form, which still needs a name and one detail.
- **Founder photo** replaces the `[Founder photo]` placeholder in the report card, which makes the card's header taller than in the design.
- **Timetable sizing is CSS, not JavaScript** (`450vh` + a sticky `100vh` pin, at 900px and up), so nothing shifts on load. Same numbers as the design.
- **Minutes chart:** 40 tiny buttons became one slider over the chart. It looks and hovers the same, passes touch-target checks, and takes arrow keys instead of 40 tab stops.
- **Teacher nudges** rotate only while on screen, and not at all with reduced motion. They aren't announced to screen readers every 2.6 seconds. On phones each nudge has a fixed height, because in the design the rotating text moved the whole page below it up and down.
- **Keyboard:** tabbing into a panel that's panned off-screen scrolls that period into view.
- **Report card rows** rest fully visible and fade in from 20% when triggered, so they read without JavaScript.
- **Fade-ins** start at opacity .01 instead of 0, so Chrome can count the hero text as the LCP element. It looks identical.
- **Contrast fixes with almost no visual change:** notebook subtitles are fully white, and the LIVE badge uses `--red` instead of `--margin`.
- **Anchors on phones** land below the taller nav.

Kept as designed, worth a decision later:
- At 390px the sticky nav wraps onto three rows and takes 189px, about 22% of the screen, all the way down the page.
